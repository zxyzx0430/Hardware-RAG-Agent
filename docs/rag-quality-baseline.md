## 1. 给非技术使用者的结论

项目值得继续开发，但下一轮应该先让已有问答“更可靠”，不是继续增加功能名称。

目前它通常能找到相关资料，也能给出处；但仍出现找到了资料却回答失败、回答漏项、照抄资料里的算术错误，以及删除资料后缓存还返回旧内容。已有聊天、手动长期记忆、Skills/MCP 和硬件工作台不需要重新搭建，重点是补实际使用和异常情况下的验收。

可以继续开发和做日常试用；**暂不把当前版本认定为 RAG 质量全面达标，也不要把它的答案直接作为无需复核的硬件设计或烧录依据。** 本轮没有修产品代码、改黄金答案、安装依赖、提交或推送。

## 4. 回答质量与评分边界

### 标准评分没有完成

实际尝试的 DeepEval 标准四指标样本 `general-G001`，仅得到上下文召回和精度，忠实性及答案相关性返回 `ValidationError`，四指标完整样本为 **0**，标准总分为 **不可用**，不是 0 分或达标。

### 补充诊断评分

为定位问题，另用同一个 `Text` 模型做单次结构化诊断：上下文召回、忠实性、回答相关性与完整性、上下文精度，以及单列的答案正确性。它是**自评式诊断，不是 DeepEval 标准分、独立专家评分或业界排行榜**。

旧版只传来源摘录，会误伤模型实际读到的父片段和合法元数据，因此旧版结果不混入最终汇总。最终 v3 同时传入成功的 Agent 检索/文档盘点工具结果、工具实际返回的父片段及来源 ID、标题、页码、分数等元数据，诊断端不再截断这些已捕获内容；产品工具本身仍有片段长度限制。评分超时和格式失败保留为空，不算作答案错误，也不悄悄重试挑选高分。

### 缺资料时的表现

- **虚构芯片/寄存器：** 实际明确拒绝给出 ZXQ-TEST-9371 的 QVREG 地址和复位值，解释了检索结果只是无关关键词匹配。没有编造要求的数值。无关结果的展示相关度仍有约 55%～73%，排序分数不是事实可信概率。该探针虽然满足形式引用链路，也不代表找到了那个不存在的寄存器。
- **空知识库：** 如实披露没有资料、没有伪造本地引用，但随后仍给通用知识并过度推广为“STM32 全系列一致”和“所有 GPIO 上电都默认输入”。[ST 官方 F1 HAL](https://github.com/STMicroelectronics/stm32f1xx-hal-driver/blob/master/Src/stm32f1xx_hal_gpio.c)使用 CRL/CRH；[F4 参考手册](https://www.st.com/resource/zh/reference_manual/DM00135183.pdf)有调试管脚复位例外。因此拒答/证据不足策略只能算局部表现良好，不能宣布全面防幻觉。

## 5. 已复现的软件问题

### P0：资料删除后仍可能出现在回答里

在隔离库创建一个唯一标识的合成片段，实际入库 1 条；第一次检索命中 1 条。删除该测试知识库后，确认数据库已不存在该 KB，再执行同一检索，仍返回已删除内容 1 条。

证据为本机 `cache-probe.json`：`kb_exists_after_delete=false`、`after_cached_hits=1`、`stale_deleted_content_returned=true`。只删除本轮新建的合成 KB，没有删除用户材料。

[search.py](../backend/src/rag/search.py)结果缓存有效期 300 秒，键包含查询、KB 范围、top_k、阈值及文档过滤，但没有资料版本。缓存命中在重新核对 KB 状态之前返回；实际复现的是删除，编辑/停用/重新索引等变更的表现仍须另测。

**建议验收条件：** 删除后下一次查询不能返回已删除内容；停用、更新、重索引、默认启用范围变化及多进程缓存分别有回归。采用版本或定向失效，不把“等五分钟”当修复。

### P0：建索引时影响其他接口响应

实际连续上传时，一次上传超过初始 60 秒等待界限；索引进行中一次 `/api/kb/list` 在 15 秒内未返回。诊断程序提高等待时间并保留已上传文档后，最终七份均成功索引，故不能把这些文件记为永久入库失败。

[kb_routes.py](../backend/app/api/kb_routes.py)的异步后台 `_index_document` 直接调用同步解析/入库；入库又执行向量写入和 BM25 重建。源码和观察支持存在阻塞事件循环的风险，但没有用线程采样精确量化每个子阶段的贡献。

**建议验收条件：** 大文档建索引期间健康检查、文档列表和聊天入口仍快速响应；有队列/工作线程或独立 worker、并发上限、进度、取消及失败状态。按项目规模选择最小可行方案，不为队列而引入完整分布式平台。

### P0：工具抓取失败却被标成执行成功

G026 和空库探针共保存 5 次 `webfetch`：内部 `data.error` 为抓取失败，外层却为 `success=true`。其中有 HTTP 301；这说明实际抓取失败/不跟随重定向，**不证明用户网络整体超时或代理损坏**。

[webfetch.py](../backend/src/agent/tools/groups/retrieval/webfetch.py)捕获错误后返回普通 dict；[tool_router.py](../backend/src/agent/core/toolkit/tool_router.py)将无异常的 dict 包成成功。这会误导 Agent 的失败恢复和审计。

**建议验收条件：** HTTP 错误、重定向策略、超时、空内容分别有明确失败/缺证据状态；不能只有内部字符串错误、外层“成功”。重定向还要保留 URL/网络访问安全校验；网页抓取入口不应承诺能解析任意 PDF。

### P1：运行状态和诊断需要补齐

- 重排器是否真正可用、是否降级，应有可见的预检和运行记录，避免“配置开启”等同于“实际启用”。
- [vector_store.py](../backend/src/rag/vector_store.py)对 NumPy `embeddings` 做布尔判断，实际重复出现数组真值不明确警告，使向量维度探测返回空。这不是已证明的全索引失败，但相关维度一致性保护需要修复和回归。
- 实际 `todo_write` 出现 `TodoOp is not JSON serializable` 审计写入警告；不能因此声称所有审计都丢失，需定向核对序列化和该次工具审计。
